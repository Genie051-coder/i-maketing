## 0. 들어가기에 앞서서

> 본 문서는 **AI 가 작성한 안내서**입니다.  
> 너무 세세하고 일일이 문자 하나씩 읽기보다는, **흐름과 문맥 위주**로 보시면 됩니다.

- 표·코드 스니펫·체크리스트 등은 참고용이며, 표현이 다소 어색하거나 중복될 수 있습니다.
- 각 섹션의 **의도**(무엇을, 왜 하는지)를 먼저 잡고, 세부 내용은 필요할 때 다시 돌아와 확인하시면 됩니다.
- 문구가 모호하다고 느껴지면 **상식적인 방향**으로 해석하셔도 무방합니다. 


> 왜 이렇게 2차 면접이 복잡한가요? 그냥 한 장소에서 시험 보는 게 더 효율적이지 않을까요?

좋은 질문입니다. 저희도 한 장소, 한 시간대에 코드베이스를 드리고 면접자분들이 그 자리에서 시작하시는 것이 더 낫다고 생각하지만, 과거에 그 방식으로 진행해본 결과 코드 이해에 할당되는 시간이 너무 많이 소요되었습니다. 그래서 take-home 으로는 '코드 이해 + 한 개의 기능 구현(코드 이해에도 도움)', on-site 로는 '이미 이해된 코드베이스에서의 구현' — 이렇게 두 개의 챕터로 나누게 되었습니다.

> 그러면 시간이 덜 드는 과제를 주면 되지 않나요?

또 좋은 질문입니다. 저희 팀이 후보자분들에게서 보고자 하는 것은 **'이해 → 응용' 과정에서의 커뮤니케이션**이기 때문에, 어느 정도 복잡한 소스 코드를 이해하시는 과정은 죄송하지만 필연적이라고 생각합니다.

> git repo 와 브랜치 전략

[https://github.com/Genie051-coder/i-maketing](https://github.com/Genie051-coder/i-maketing) 은 오후 3시부터 public 으로 공개됩니다.
`dev` branch 에서 `본인닉네임/{원하는 브랜치 목적에 맞는 이름}` 으로 branch out 하셔서 진행하시면 됩니다.
이 repo 가 닫히는 시간은 따로 없으나, 이 과제에는 최대 3시간까지만 사용해주세요.
시작 시점은 저희가 따로 잴 수 없으니, 양심에 시간 제한을 맡기겠습니다.

## 1. 과제 개요

이 과제는 실제 운영 중인 이메일 마케팅 플로우 빌더 (`i-marketing`) 코드베이스를 이해하고,  
주어진 기능 개선 요구사항을 구현한 뒤 결과를 정리·발표하는 과정입니다.

| 구분 | 내용 |
|------|------|
| **프로젝트** | i-marketing — 이메일/SNS 캠페인 플로우 빌더 |
| **스택** | Next.js 15, React 19, TypeScript 5, Zustand 5, Prisma 5, Tailwind CSS v4 |
| **메인 과제** | `FEATURE_EMAIL_PREVIEW.md` 구현 |
| **추가 과제** | 현재 소스 코드에서 개선하고 싶은 부분 1가지 선정 및 설명 (구현 X) |

## 2. 준비 단계 — 코드베이스 이해

개발을 시작하기 전, 아래 순서로 문서와 코드를 파악하세요.

### Step 1. 앱 온보딩 흐름 파악 → `ONBOARDING.md` 읽기

- 사용자가 `/ko` 홈에서 캠페인을 생성하고 이메일을 발송하는 전체 흐름을 확인합니다.
- 각 단계에서 어떤 노드(Node)가 사용되는지, 화면 다이어그램을 통해 UI 구조를 파악합니다.

### Step 2. 실제 유스케이스 체험 → `useCase1.md` 따라하기

- 앱을 직접 실행하여 `useCase1.md`의 단계를 따라가며 실제 UX를 경험해보세요.
- 마지막 `발송 확인` 노드의 미리보기 영역이 정적 placeholder 텍스트("이메일 콘텐츠 미리보기")만 보여주는 것을 직접 확인하세요. → 이것이 메인 과제에서 해결할 문제입니다.

> **앱 실행 방법** (최초 1회)
> ```bash
> docker-compose up
> npm run dev                   # Next.js 개발 서버 (http://localhost:3000)
> ```

### Step 3. 아키텍처 이해 → `ARCHITECTURE.md` + 소스 코드

아래 파일들을 순서대로 읽으며 (무조건 읽으실 필요 없습니다, 자신이 실제 코드를 보고 이해하는 타입이라면 문서는 굳이 보지 않아도 됩니다, 결국 이 문서도 ai 가 만든 참고용 문서이니까요.) 코드 구조를 파악합니다.

| 우선순위 | 파일 | 이유 |
|---------|------|------|
| ★★★ | `src/features/nodes/email-confirm-send/ConfirmSendConfig.tsx` | 메인 과제 수정 대상 핵심 파일 |
| ★★★ | `src/features/nodes/email-create/ui/EmailDropZone.tsx` | `renderBlockContent` 재사용 대상 |
| ★★ | `src/features/nodes/email-create/types.ts` | `EmailBlock` 타입 정의 |
| ★★ | `src/features/Flow/store/useFlowStore.ts` | `nodes` 상태(이메일 노드 data) 접근 |
| ★ | `ARCHITECTURE.md` | 전체 아키텍처 참고 |

## 3. 개발 과제 (메인)

### 메인 과제 — `FEATURE_EMAIL_PREVIEW.md` 구현

요구사항 문서: **`FEATURE_EMAIL_PREVIEW.md`**

마지막 노드(`발송 확인`)의 이메일 미리보기 영역에 실제 이메일 블록 내용을 렌더링합니다.

- **현재**: `발송 확인` 노드의 미리보기 섹션이 "이메일 콘텐츠 미리보기" 정적 텍스트만 표시.
- **목표**: 사용자가 `이메일 작성` 노드에서 구성한 실제 블록(blocks)을 미리보기 영역에 그대로 렌더링. PC / 모바일 토글에 따라 너비가 달라지도록.

**핵심 수정 파일**
```
src/features/nodes/email-confirm-send/ConfirmSendConfig.tsx
```

**재사용 대상**
```
src/features/nodes/email-create/ui/EmailDropZone.tsx   (renderBlockContent)
src/features/nodes/email-create/types.ts               (EmailBlock 타입)
src/features/Flow/store/useFlowStore.ts                (nodes 상태)
```

> 구체적인 구현 방법, Props 변경, 코드 스니펫, 체크리스트는 `FEATURE_EMAIL_PREVIEW.md` 의 각 섹션을 참고하세요.

## 4. 개선 사항

> **구현은 하지 않습니다.**  
> 현재 소스 코드에서 개선하고 싶은 부분을 **하나만** 선정해서 **왜** 개선이 필요한지, **어떻게** 개선할 것인지를 설명해주세요.

### 작성 예시

| 항목 | 내용 |
|------|------|
| **개선 대상** | 어떤 파일/컴포넌트/모듈을 개선할 것인지 |
| **현재 문제점 (Why)** | 현재 구조의 문제, 잠재적 버그, 성능/유지보수성/UX 측면의 한계 |
| **개선 방향 (How)** | 어떤 방식으로 바꿀 것인지 (구조 변경, 패턴 도입, 라이브러리 도입, API 분리 등) |
| **기대 효과** | 개선 후 얻을 수 있는 이점 |

### 작성 분량 (권고)

- **자유 양식**, 짧게는 5줄 ~ 길게는 1페이지 수준이면 충분합니다. ( 양은 중요 하지 않습니다.)
- 다이어그램은 언제나 환영입니다.
- 코드 스니펫(현재 코드 / 개선 코드)을 포함하면 설명이 더 명확해집니다.

### 선정 팁

- 메인 과제(`FEATURE_EMAIL_PREVIEW.md`)를 진행하면서 **"이 부분은 좀 어색한데?"** 싶었던 코드를 자연스럽게 떠올려 보세요.
- 거창한 리팩토링이 아니어도 됩니다. 작은 네이밍/타입/구조 개선도 환영합니다.
- 본인이 가장 자신 있게 설명할 수 있는 주제를 고르세요.

## 5. 3번이 이해되지 않을 때

`FEATURE_EMAIL_PREVIEW.md` 의 요구사항이 도저히 이해되지 않거나, 구현에 진입하지 못해 막혔다면 — **메인 과제를 포기하지 마시고 아래로 전환하세요.**

> **`FEATURE_EMAIL_PREVIEW.md` 구현 대신, [4. 개선 사항] 에서 본인이 선정한 "현재 소스 코드의 개선하고 싶은 사항"을 직접 구현해주세요.**

즉, 둘 중 하나는 반드시 **동작하는 결과물**로 가져와 주세요.

| 케이스 | 산출물 |
|--------|--------|
| 메인 과제(`FEATURE_EMAIL_PREVIEW.md`)를 이해하고 진행하는 경우 | ① 메인 과제 구현 + ② 개선 사항 **설명** (구현 X) |
| 메인 과제가 이해되지 않는 경우 | ① 개선 사항을 **직접 구현** (메인 과제 대체) |
